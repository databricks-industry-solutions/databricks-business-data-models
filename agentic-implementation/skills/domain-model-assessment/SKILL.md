# Domain Model Assessment Skill

> **⚙️ Load `autonomous-validation` alongside this skill — it is NOT pulled in automatically; nothing wires the two together, so load it explicitly at the session start.** (See its `When to Load` for the execution-discipline contract.) — it also hosts `commentary-protocol.md`, the closeout this skill emits.
> Assessment is read-only on the data layer, but it still runs many bronze-profiling queries and the one permitted metamodel edit (Phase 2C / Step 2.7), and the Completion Self-Audit (Critical Rule 15) leans on its "surface what's left, don't prod" gate.

## Overview

This skill drives the **full lifecycle of assessing and iterating a V2 domain (vibe) model**:
from inspecting an empty target model through profiling bronze sources, evaluating existing
production silver/gold models for integration, producing source-to-target mapping reports,
running a structured gap-close iteration loop, and generating pre-filled handoff documents
for the ETL Development Framework.

Proven on the Acuity Manufacturing Vibe V2 domain discovery (July 2026). Reusable for any
Acuity domain model generated by the vibe modelling agent.

**How we treat the model.** The vibe model is a **one-shot, pre-iterated frozen input** — a
coherent starting point the customer has (often) already iterated on *before* entering this
loop. We deliberately diverge from the vibe-modeling blog's "regenerate via the model-agent"
story: **there is no model-agent regeneration in this motion.** The only edit mechanism this
skill uses is **Genie Code** — scoped SQL against the `vibe_metamodel_*` tables. When discovery
finds the model genuinely misses the mark, the skill calls it out and hands the user two
disposition paths: (1) **iterate upstream** — emit **vibe-model prompts** (natural-language
instructions the user takes to the vibe-modeling agent to refine the model before the build),
the recommended path for structural misses; or (2) **edit in place via Genie Code** — a scoped
metamodel SQL edit for small additive/corrective changes. The model is revisable, not sacred.

**What this skill produces:** *(all written to `docs/design/` in the domain project folder —
NOT the project root or a bare `docs/`. Author-provided input docs are the only exception: they
live in `docs/inputs/` per Phase 0. See Phase 4/6 and Critical Rule 11.)*
- `Source-to-Target Mapping Report` — per-table: intent, candidate sources, column map,
  key derivation, FK resolution, fit grade (Full / Partial / Blocked), gaps & ingestion asks
- `Model Completeness Assessment` — reverse check: what bronze data exists that the model
  doesn't cover? Identifies candidate new entities, missing hierarchy levels, grain extensions.
- `Model Assertion Validation` — surgical check: where does profiled bronze *contradict* the
  model's declared grain / type / PK-uniqueness / FK-cardinality? (Step 2.7)
- `next_vibes.md` — **default output every run** (model-agent format; coherence-only per the bright
  line) — Model Quality Score header, PRIORITY lines (business-coherence verbs: `connect_table`,
  `remove_fk`, `rename_product`, `rename_attribute`, `add_column`, `remove_product`,
  `remove_attribute`), static-analysis findings, deterministic score. Even a perfect model emits
  it (high score + "No structural refinements recommended" line). The Gap & Enhancement Registry
  remains the ingestion-ask artifact; `next_vibes.md` is the model-refinement artifact.
- `docs/commentary/assessment-improvement-recommendations.md` — **emitted at closeout every run** (skill-improvement recommendations, following `autonomous-validation/commentary-protocol.md`). The skill-improvement analog of `next_vibes.md` — a clean run records what worked; an imperfect run captures friction and recommendations for this skill.
- `Integration Assessment` — whether existing production silver/gold can fold in as-is,
  be consumed as source, or should become downstream of V2 Silver
- `Gap Registry` — prioritised list (P0–P3) of blocked columns/tables with unblock actions
- `Discovery Report Amendments` — revised grades after existing-model analysis
- `Domain Readiness Summary` — final scorecard, load order, exit criteria evaluation
- `business_requirements.md` — pre-filled ETL framework requirements doc (handoff)
- `etl_detailed_spec.md` — pre-filled ETL framework detailed spec (handoff)

**Scope:** Read-only discovery against **data** (bronze / silver / gold) — no CREATE / INSERT /
MERGE / COPY into any data table. The **one permitted write** is a **metamodel edit via Genie
Code** (scoped SQL against the `vibe_metamodel_*` tables), and only at the Phase 2C / Step 2.7
human gate when the user picks the edit-in-place disposition. All data-layer writes happen in a
subsequent build session using the `etl-development-framework` skill.

## Two halves: knob-blind reconciliation, knob-aware target shaping

This assessment produces **a buildable, per-domain schema seeded by the vibe model and reconciled
against bronze** — not a "faithful port." The build's output shape is a customer choice
(`conventions.yml` → `output_model`: `normalized` | `dimensional` | `hybrid`, default
`normalized`). The assessment splits cleanly along that knob, and getting the split right is what
prevents silent descoping:

- **KNOB-BLIND — semantic reconciliation (the valuable core).** Grading model↔data **both ways**,
  fit grades (Full / Partial / Blocked), the Model Completeness Assessment, Model Assertion
  Validation, and the Gap & Enhancement Registry. This reasons about *business entities and
  whether the data supports them* — it is **identical in all three modes**. The knob must NEVER
  influence it, or you reintroduce the bias in a new hat ("we're building a star, so this
  normalized-only entity doesn't matter → drop it").
- **KNOB-AWARE — target shaping.** The source-to-target *map*, key derivation (surrogate vs
  natural), grain decisions, and the pre-filled handoff spec. Here the knob steers:
  - `dimensional` → S2T targets `dim_/fact_/bridge_`, surrogate `{Entity}_Key`, conformed dims.
  - `normalized` → S2T targets **product-named 3NF tables**, the model's `{product}_id` PKs.
  - `hybrid` → two target tiers built in sequence (normalized 3NF silver first, THEN a
    dimensional gold star downstream from it) — layered, not both-shapes-at-once.

> **Assess the business truth knob-blind; project the target shape knob-aware.**

**No silent descoping (MANDATORY).** A modeled entity/attribute with no bronze source is **never
dropped** — it is recorded **DEFERRED** with a future-enhancement callout ("needs bronze {X}").
The symmetric direction (bronze reveals meaning the model missed) surfaces as a **proposed model
addition**. Both land in the Gap & Enhancement Registry the DE team reviews per domain. "The data
isn't here yet" is a finding, not a decision. This behavior is knob-blind.

### Two loops & the bright line (MANDATORY, knob-blind)

This motion runs **two complementary feedback loops that must never overlap**:

| Loop | Artifact | Direction | Answers |
| --- | --- | --- | --- |
| **Ingestion / "get more data"** | **Gap & Enhancement Registry** (P0–P3 asks) | data → catches up to model | "You modeled X, no bronze — go get source {Y}." |
| **Model refinement** | **`next_vibes.md`** | model → truer to the business | "Here's how to make the *model itself* better." |

**Bright line:** `next_vibes.md` removes or renames a table/column **only for business *coherence***
(the model is wrong about the business — a Step 2.7 contradiction, or a user assertion that a concept
doesn't apply). It **never** removes for *absence of data* — that pressure belongs to the Gap Registry
(ask for the source) and to the deviation mechanism (a reversible build-time drop). `next_vibes.md`
is fed to the data-agnostic vibe-modeling agent, so it describes the **business**, not the customer's
current ingestion footprint. The two loops are complementary, never overlapping.

**`next_vibes.md` is a required default output emitted on every run** — even for a perfect model
(which emits a high score and a "No structural refinements recommended" line). It is in the
model-agent's exact format (Model Quality Score → PRIORITY lines → static-analysis findings →
deterministic score), governed by the bright line: removals and renames only for business
*coherence*, never for absence of data. The **Gap & Enhancement Registry remains the
ingestion-ask artifact**; `next_vibes.md` is the model-refinement artifact.

## Mode Gate — which layer are you assessing? (run first)

This skill has **two modes**. Before Phase 1, resolve which one applies from `conventions.yml`
`output_model` + the state of the target layer:

| Condition | Mode | Path |
| --- | --- | --- |
| Source layer is **bronze**; silver target is empty (any `output_model`) | **A — bronze → silver discovery** | The phase model below (unchanged). This is the default and the common case. |
| `output_model` is `hybrid`, **silver 3NF already exists (populated)**, and the ask is to derive the downstream **gold star** | **B — silver → gold derivation** | Skip the bronze-centric steps; run `gold-derivation-protocol.md`. |

- **Mode B is `hybrid`-only** — it is the *second* pass of a hybrid engagement. Pass 1 = Mode A
  (assess bronze → build the normalized silver 3NF). Pass 2 = Mode B (derive the dimensional gold
  star from the built silver), run **later**, after the silver build lands. Never design the gold
  star during the silver pass — see `source-to-target-mapping.md` "Mode-Specific Report Scope".
- **`dimensional` is always Mode A** — the `dim_/fact_/bridge_` star IS the silver target, derived
  directly from bronze in one pass. There is no separate gold star to derive; its gold layer is
  marts + metric views built over the silver star (see `etl-development-framework/gold-and-metrics.md`),
  not a re-derived dimensional model. Do NOT route `dimensional` to Mode B.
- **`normalized`** is always Mode A, single tier — Mode B never applies.

**Gold is handled in FOUR roles now — keep them distinct:**
1. Gold **as source** (Mode A, Step 2.5) — demote a Blocked grade.
2. Gold-shaped **mis-homed silver** (Mode A, Step 3.4) — re-home to gold.
3. Gold **as coverage oracle** (Mode A, Step 3.8) — grade whether new silver supports existing gold KPIs.
4. Gold **as derivation target** (Mode B, `gold-derivation-protocol.md`) — *design a new* gold star
   from built silver, in `hybrid` mode only. **This is the new capability** the first three did not cover.

## When to Load This Skill

Load when:
- A discovery brief is handed in (`type: research`, mentions a vibe model or domain model)
- User asks to "do discovery", "assess a domain model", or "find source data for a model"
- User asks whether an existing silver/gold model can be "folded into" or relates to a V2 domain
- User hands a domain model schema (empty tables with metamodel) and asks what can populate it
- Starting a new iteration pass after a gap-close action (new ingestion landed, existing model found)
- Re-assessing the **same** vibe model + **same** bronze already assessed for a different knob
  (only `etl_type`/`output_model` differs, e.g. a `merge_notebook` build now being done as
  `sdp_pipeline`) — take the **abbreviated re-assessment path** (`model-completeness-protocol.md` Phase 2B.1):
  gate on a quick row-count check, reuse the prior Phases 1–2C findings, regenerate only Phase 4/6.
- User says "start the build" or "generate handoff docs" after discovery is complete
- User asks whether the model is complete or missing anything
- **(Mode B)** `output_model` is `hybrid`, the silver 3NF is built, and the user asks to
  "assess/derive/design the gold layer" or "build the gold star" — route to `gold-derivation-protocol.md`

Do NOT load for:
- Building DDL or MERGE notebooks — use `etl-development-framework` instead
- General SQL profiling without a target domain model — use `data-sampling` instead

## Execution Model

### Phase −1 — Config Bootstrap (run before Phase 0)

If `conventions.yml` is **absent** at the output root, do NOT error, guess, or assume defaults —
run the interactive bootstrap in `config-bootstrap.md`: Q&A-first with plain-English explainers for
each knob (`output_model`, `etl_type`, catalogs, …), an opt-in read-only workspace probe to pre-fill
catalog/metamodel/bronze answers, then write and confirm a populated `conventions.yml` (seeded from
this skill's own `templates/conventions.yml` basic seed, mode keys from the matching repo-root
`conventions-variants/*.yml` overlay when reachable, else from the Q&A). Only once the
config is written and confirmed do you proceed to Phase 0. If `conventions.yml` is already present,
skip Phase −1 entirely.

### Phase 0 — Intake (run before anything else)

The output root at flow start contains `conventions.yml` and possibly loose requirement `.md`
files that do not follow the established doc patterns. Before assessing:

1. Detect `.md` files at the output root or directly in `docs/` that are NOT skill-generated
   artifacts (i.e. not one of the known `design/`, `.pipeline/`, tutorials/contributor names).
2. `git mv` each into `docs/inputs/` verbatim — preserve filename, do not rewrite content.
3. Treat `docs/inputs/` as READ-ONLY source material. The synthesized/enriched versions you
   produce (e.g. an authoritative `business_requirements.md`) are written to `docs/design/`,
   never back into `inputs/`.
4. If no loose files exist, do not create `docs/inputs/`.

**Fresh-start declaration.** If the user explicitly says "ignore previous iterations" / "start
fresh" / "new assessment":
1. Do NOT reference or inherit grades, mappings, or source evidence from prior S2T reports, build
   manifests, or etl specs in the same project tree.
2. DO note the *existence* of prior schemas (informational — populated tables, prior versions) but
   do not fold their conclusions into this pass.
3. Mark the report header: "Fresh assessment — prior iterations ignored per user request."
4. "Fresh" means *don't inherit conclusions*, NOT "re-run queries you don't need to" — the
   abbreviated re-assessment gate (`model-completeness-protocol.md` Phase 2B.1) still applies if the model +
   bronze are unchanged from a sibling.

This supports users who author requirements themselves (silver or gold) instead of using
vibe-model outputs.

### Phase 1 — Inspect the Target Model
**First (Step 1.0): locate the metamodel — do not assume its layout.** Resolve `{metamodel_schema}`
+ `{mm_prefix}` from `conventions.yml` (`vibe_model.metamodel_schema`/`metamodel_prefix`) or by
probing `information_schema` — the tables are either co-located + prefixed (`vibe_metamodel_*`) or
bare-named in a separate `_metamodel` schema. **Then scope to this domain + one version:** a shared
metamodel holds every domain and every version, so the `product`/`attribute` queries MUST filter by
domain (via the `domain` table) and a single resolved version (default = MAX for this domain).
Run the metamodel inspection queries from `discovery-protocol.md` (§1.0 → §1.6).
**Outputs:** Resolved metamodel location + version (recorded in the report header), business context
row, table inventory (product), full column inventory (attribute), FK graph (via
`key_column_usage` join, with `foreign_key_to` fallback), glossary tags (column_tags).
**Degenerate placeholders — auto-exclude as an explicit Phase 1 output, do not defer to the human
gate.** Immediately after Step 1.2 (product inventory), list any degenerate placeholder (single
column, null/empty description, null type — generator artifacts, not real entities) and state:
"Excluding N degenerate placeholder(s): {list}. These are generator artifacts (single-column
schema, no description), not real entities." **Auto-exclude and notify** — do not carry them to the
Phase 2C human gate as a decision item (the user can still override if they disagree). Record the
count in the report header.

### Phase 2 — Profile Bronze & Existing Development Sources
Search bronze schemas by system module + keyword. Profile row counts and column lists.
**Run Step 2.4b Source Column Reconciliation for every entity** — reconcile each metamodel TARGET
attribute name against the actual `information_schema` bronze column, emit `source_table.source_col`,
and flag no-match as Derived/GAP. The metamodel attribute is the target name, NOT the bronze column
name — skipping this is what caused 76% of files to be rewritten downstream. Collect date formats
per source system (Step 2.4c) and run the **All-STRING fast path** where every column is STRING.
Run **Step 2.8 Cross-Domain FK Availability** to grade each cross-domain parent Resolvable /
Deferred / Blocked. Inventory any existing V1/MVP model in the workspace for proven-mapping evidence.
Run the **Step 2.6 Mutability Probe for every fact** (entity semantics + creation-vs-update
timestamp divergence) — this, not row count, decides `APPEND_ONLY` / `INCREMENTAL_MERGE` /
`SDP` and names the watermark column. **When `etl_type: sdp_pipeline`, translate that label to an
SDP object type (MV / Streaming Table / AUTO CDC / incremental `REPLACE WHERE` flow) via
`sdp-strategy-mapping.md`** — the MERGE-era labels don't map 1:1 to SDP objects, and a large mutable
fact in particular needs the REPLACE-WHERE-vs-AUTO-CDC decision, not a default MV.
Run **Step 2.7 Model Assertion Validation** — the **surgical lens** — for every entity:
profile bronze to test the model's *declared* grain / type / PK-uniqueness / FK-cardinality and
surface contradictions. This complements the Step 2.6 mutability pointer and feeds the **same
human gate as Phase 2C** (never auto-correct).
Read `discovery-protocol.md` for search patterns and both probes; `model-completeness-protocol.md` for the V1 inventory protocol.
**Outputs:** Confirmed source table list per entity; row counts; V1 proven-mapping table;
per-fact mutability result (pct_mutated + watermark column) feeding S2T Load strategy + spec
Section 5; Model Assertion Validation findings (contradictions → decisions at the human gate).

### Phase 2C — Model Completeness Assessment
**CRITICAL — Do not skip this.** The vibe model is a starting point, not gospel.
After profiling all bronze sources, run the reverse check from `model-completeness-protocol.md` Phase 2C:
1. Identify ALL bronze tables NOT mapped to any V2 entity — exhaustive, no absolute row-count gate
   (a fixed >10K threshold drops real candidates in small-domain datasets; let categorization filter)
2. Categorise each: candidate new entity, missing hierarchy, grain extension, cross-domain, subordinate detail
3. Check business process coverage: enumerate known domain processes, confirm each has an entity
4. Present the Model Gap Candidates table — each row carries a **Suggested next_vibes.md action** —
   and route findings to the single human gate. Two disposition paths for a confirmed miss:
   **(1) iterate upstream** (recommended for structural misses — user takes the emitted
   vibe-model prompts to the vibe-modeling agent, refines the model, re-enters via Trigger E
   with V+1), **(2) edit in place via Genie Code** (scoped `vibe_metamodel_*` SQL for small
   additive/corrective changes). Plus the existing leave-as-gold-only / out-of-scope /
   attribute-enrichment options. Step 2.7 (surgical) findings route to this **same** gate.
   When `model_deviation` toggles are on, the same gate also offers **DROPPED (deviation)**
   (for a 100%-null column, an FK to an unbuilt domain, or a no-process/no-source table) and
   **NET-NEW proposal** (for bronze-revealed additions, propose→build) — both human-confirmed
   and logged.
**Gate:** Human must confirm disposition of each candidate before model is considered final.
**Outputs:** Model Gap Candidates table (with Suggested next_vibes.md action column); Business
Process Coverage Check; `next_vibes.md` PRIORITY lines for structural misses; user decisions recorded.

### Phase 3 — Assess Existing Silver / Gold for Integration
For every production silver or gold schema in scope, run the grain analysis, naming comparison,
and purpose classification from `existing-model-assessment.md`. Then run **Step 3.8 — Existing
Gold / Dashboard KPI Coverage**: discover legitimately-gold models and the KPIs/metrics they
(or their dashboards) compute, and grade whether the new silver model **supports** each KPI
(Supported / Partial / Unsupported) — the comprehensiveness oracle. Keep this distinct from the
two other gold roles: Step 2.5 uses gold **as a source** (to demote a Blocked grade); Step 3.4
catches a **gold-shaped table mis-homed as silver**; Step 3.8 grades a **legitimately-gold model
as a first-class KPI-coverage target**. Unsupported *structural* KPIs become P-items and
`next_vibes.md` PRIORITY lines, routed to the same human gate as Phase 2C / Step 2.7.
**Outputs:** Integration Option recommendation (A/B/C), grade uplifts, source-quality uplift
table, KPI-coverage table (Supported / Partial / Unsupported), and `next_vibes.md` PRIORITY lines for
unsupported structural KPIs.

### Phase 4 — Produce Source-to-Target Mapping Report
For each real target table (load order: masters first, facts last), produce:
intent, candidate sources, column map, key derivation, FK resolution, fit grade, gaps.
Follow the format in `source-to-target-mapping.md`.

- **Carry the metamodel's comment content forward:** populate each column row's `Metamodel description` (from `vibe_metamodel_attribute.description`, pulled in Phase 1.3) and `Glossary term` (from `business_glossary_term`), and each entity's table-level `Metamodel description` (from `vibe_metamodel_product.description`). A column with neither gets `—` (never blank). These seed the built COMMENT + `glossary_term` tag — see `etl-development-framework/naming-standards.md` §5.6.

**Outputs:** S2T Mapping Report saved as **`docs/design/s2t_map.md`** in the domain project folder
(stable snake_case name — NOT a dated title-case filename; create `docs/design/` if absent; do NOT
write it to the project root or a bare `docs/`); scorecard; ingestion ask table.

### Phase 5 — Iteration Loop
After delivery, user returns with: new ingestion landed, existing model found, architecture decision, or correction.
Run the iteration protocol from `iteration-loop.md` to re-grade affected tables and update.
**Gate:** Iteration ends when no Blocked tables remain, or remaining Blocked are accepted as out-of-scope.
**Human-in-the-loop gate:** User must explicitly confirm exit criteria before proceeding to Phase 6.

#### Phase 5 → 6 Completion Self-Audit (MANDATORY — render unprompted before any "start the build")

**Do not wait to be asked "are we done?"** Before accepting *any* "start the build" signal and
before generating a single handoff doc, render the audit table below — the user must not have to
ask for it. Reconcile every closing obligation and report a single **"Remaining before handoff"**
list. **An empty Remaining list is the ONLY state that unlocks Phase 6.** If any item is open,
present the list and stop — do NOT generate the handoff docs (this leans on `autonomous-validation`'s
"surface what's left, don't prod" contract; see Critical Rule 15).

| # | Closing obligation | Done when | Status |
| --- | --- | --- | --- |
| 1 | **Every in-scope entity has a fit grade** | No entity is ungraded — each is Full / Partial / Blocked | ☐ |
| 2 | **Every Blocked entity has a disposition** | Accepted out-of-scope, logged as a P0–P3 ingestion ask, or slated to a later wave — none dangling | ☐ |
| 3 | **Every Phase 2C / Step 2.7 finding has a recorded disposition** | Each is iterate-upstream / edit-in-place / gold-only / out-of-scope / attribute-enrichment / DROPPED (deviation) / NET-NEW (deviation) — none open | ☐ |
| 4 | **Required `docs/design/` artifacts exist** | S2T Mapping Report (`docs/design/s2t_map.md`, stable snake_case name) + Gap & Enhancement Registry + Domain Readiness Summary all written | ☐ |
| 5 | **(gold in scope) KPI-coverage table produced** | Step 3.8 Supported/Partial/Unsupported table present; Unsupported → P-items | ☐ |
| 6 | **Metamodel comment content carried** | Every in-scope column row has a `Metamodel description` + `Glossary term` (or an explicit `—` with reason), and each entity carries its table-level `Metamodel description` | ☐ |
| 7 | **Every NULL_SOURCE column has a keep/drop disposition** | The interactive keep/drop gate ran; each always-null column is marked keep or drop (domain default set + per-column recorded in `etl_detailed_spec.md`) | ☐ |
| 8 | **`next_vibes.md` written** | Emitted this run in model-agent format (high-score + "no refinements" line if the model is clean) | ☐ |

**Deviation escape-hatch surfacing (unprompted).** If Partial/Blocked entities remain AND
`model_deviation` is effectively off, state — before the "Remaining before handoff" line —
"N entities are Partial/Blocked. The default is accept-and-defer (recorded as ingestion asks). If
you'd rather ship silver now, you can enable `model_deviation` (drop these / add net-new). Here is
what each toggle would drop: {per-toggle list (consult each toggle's definition in `conventions.yml`)}." This makes the escape hatch discoverable exactly at
the perfect-vs-good moment, without weakening the safe default.

Report as: **"Remaining before handoff: {list, or 'none — ready for build'}"**. Only on "none"
do you proceed to Phase 6.

### Phase 6 — Handoff Document Generation
After the Completion Self-Audit reports "none remaining", exit criteria are satisfied, and user confirms "start the build":
Generate pre-filled `business_requirements.md` and `etl_detailed_spec.md` in the format
expected by the `etl-development-framework` skill. These documents satisfy the ETL framework's
requirements gate (graded B or better) and provide a complete detailed spec that skips
the ETL framework's own discovery phase.
Read `iteration-loop.md` "Handoff to ETL Development Framework — Document Generation" for
the mapping protocol and quality gate.
**Outputs:** Three markdown files saved to `docs/design/` in the domain project folder (create it
if absent; NOT the project root or a bare `docs/`): **`docs/design/business_requirements.md`**,
**`docs/design/etl_detailed_spec.md`**, and **`docs/design/next_vibes.md`**. The first two are
exactly where `etl-development-framework` looks for them (`iteration-loop.md` "Handoff … Document
Generation"); a file dropped one level up in `docs/` will not be found by the build.
Plus **`docs/commentary/assessment-improvement-recommendations.md`** (see Closeout step below).
**Gate:** All buildable entities have confirmed sources, natural keys, and SHA2 formulas.

**Decisions recorded in handoff docs (inherited by the ETL skill — do not re-decide in the build):**
- **`etl_language`** (from `conventions.yml`, default `sql`) — records whether the build should
  generate SQL or Python (spark.sql-hosted) MERGE/validation notebooks. Surface it in the
  handoff so the ETL skill doesn't re-decide. DDL and documentation stay SQL regardless. See
  `etl-development-framework/deployment-and-dab.md` "Notebook-format contract".
- **Model-edit dispositions** — for each Phase 2C / Step 2.7 finding, record which path the user
  chose: **iterate upstream** (with the emitted **vibe-model prompt** carried as a handoff
  artifact so the build knows a V+1 is pending, or already re-entered via Trigger E) or **edit
  in place via Genie Code** (with the scoped metamodel SQL that was run). Any structural miss the
  user chose NOT to act on is recorded as a scope decision, not silently dropped. There is **no
  model-agent regeneration** at any point.

**Closeout — Emit improvement recommendations.** As the final step of the run, after the Completion Self-Audit reports "none remaining", write `docs/commentary/assessment-improvement-recommendations.md` following `autonomous-validation/commentary-protocol.md`. Always emit it (a clean run records what worked). Fold any unresolved items from a prior copy forward.

## Critical Rules (Always Apply)

1. **Load `discovery-protocol.md` before running a single query** — contains proven query set.
1a. **Locate the metamodel and scope it before mapping anything.** Never assume the metamodel is
    co-located or prefixed — resolve `{metamodel_schema}` + `{mm_prefix}` first (Step 1.0), because
    the tables may be bare-named in a separate `_metamodel` schema. And never run `product`/
    `attribute` UNSCOPED: a shared metamodel spans many domains and many versions, so filter to
    THIS domain (via the `domain` table) and ONE resolved version (default = MAX for the domain).
    If a raw row count looks inflated or a `table_name` repeats, you have NOT scoped — stop and
    scope before proceeding. Record the resolved metamodel location + version in the report header.
1b. **If `conventions.yml` is absent, bootstrap it interactively (Phase −1) before assessing.**
    Never fabricate a config or silently assume defaults — run `config-bootstrap.md`, explain each
    knob, offer the opt-in read-only probe, and write + confirm the file first.
2. **Data is read-only; the metamodel is the one permitted write.** No CREATE / INSERT / MERGE /
   COPY into any **data** table (bronze / silver / gold) in this phase — all data-layer writes
   happen in the build. The **single carve-out** is a **metamodel edit via Genie Code** (scoped
   SQL against the `vibe_metamodel_*` tables), permitted **only** at the Phase 2C / Step 2.7
   human gate and **only** when the user chooses the edit-in-place disposition. Everything else
   the skill produces is markdown.
3. **Base every "intent" on `vibe_metamodel_product.description`** — never guess at table purpose.
4. **Use V1/MVP row counts as ground truth** — if V1 loaded N rows from a source, that source
   is confirmed for the same entity in V2.
5. **Grade conservatively** — Partial = at least one significant column group ungappable.
   Full = <10% of business columns are gaps. Blocked = primary natural key has no source.
6. **Produce the Gap Registry in every report** — every pass must list P0–P3 ingestion asks.
7. **Treat existing gold in both roles — as a source AND as a coverage oracle.**
   - **As a source (Step 2.5):** check production gold schemas before declaring an ingestion
     ask — they often contain processed versions that a bronze-only search misses, and finding
     one can demote a Blocked grade. Keep this check intact.
   - **As a first-class target (Step 3.8):** legitimately-gold models and their dashboard
     KPIs/metrics are the **comprehensiveness oracle** — grade whether the new silver model
     *supports* each existing KPI (Supported / Partial / Unsupported). Unsupported structural
     KPIs become P-items and `next_vibes.md` PRIORITY lines.
8. **Run existing-model-assessment.md analysis before recommending fold-in** — most production
   silver models are Gold-pattern (use-case specific) deployed in the wrong layer.
9. **Load order from FK graph is mandatory** — derive tier sequence before mapping.
10. **Produce amended scorecard after Phase 3** — report must show pre- and post-integration grades.
11. **Generate handoff docs at exit, in `docs/design/`** — never just tell the user to "fill the
    templates manually." The discovery skill has all the data; produce the filled documents
    automatically, and write every generated artifact to **`docs/design/`** in the domain project
    folder (create the folder if absent). Do NOT drop them in the project root or a bare `docs/` —
    that is where `etl-development-framework` looks (`docs/design/business_requirements.md`,
    `docs/design/etl_detailed_spec.md`); a misplaced file is an unfound file. Author-provided *input*
    docs are the sole exception — those live in `docs/inputs/` (Phase 0).
12. **Never treat the vibe model as 100% accurate — run BOTH lenses.** The model is editable
    based on real data and business processes, so profile against it two ways, both mandatory:
    - **Additive lens — Phase 2C (Model Completeness Assessment):** what did the model *omit*?
      Entities, hierarchy levels, or grains the bronze data supports but the model lacks.
    - **Surgical lens — Step 2.7 (Model Assertion Validation):** what did the model *assert*
      that the data *contradicts*? Declared grain / type / PK-uniqueness / FK-cardinality tested
      against profiled bronze.
    Completeness alone is not enough — a model can be complete yet wrong about a grain or a key.
    Both lenses feed the **same** human gate.
13. **Present model changes as decisions, not assumptions** — when either lens finds an issue,
    present evidence and let the user decide the disposition (see Rule 14). Do NOT auto-add,
    auto-flatten, or auto-correct.
14. **No model-agent regeneration — iterate upstream or edit in place.** The model is a one-shot,
    pre-iterated frozen input; never send it back through the model-agent. When a lens shows the
    model misses the mark, emit a **vibe-model prompt** (a natural-language instruction for the
    vibe-modeling agent, surfaced in `next_vibes.md`) and offer two dispositions at the human gate: (1) **iterate upstream** —
    the user takes the prompts to the vibe agent, refines the model, and re-enters via
    iteration-loop **Trigger E** with V+1 (recommended for structural misses); or (2) **edit in
    place via Genie Code** — a scoped `vibe_metamodel_*` SQL edit for small additive/corrective
    changes. Both are the same gate; emitted prompts are a handoff artifact.
15. **Run the Completion Self-Audit before handoff — unprompted.** Exit is not the user's job to
    police. Before accepting any "start the build" and before writing a single handoff doc, render
    the Phase 5 → 6 Completion Self-Audit table and report a single **"Remaining before handoff"**
    list. An **empty** list is the ONLY state that unlocks Phase 6; if anything is open, present it
    and stop. Never treat "start the build" as license to skip the audit — the audit runs first,
    every time.
    The audit now also confirms the metamodel's own comment content (column `Metamodel description` + `Glossary term`, table-level `Metamodel description`) was carried into the handoff — an empty cell must be an explicit `—`, not an omission.
16. **Deviation is opt-in, gated, and logged — never silent, never model-agent regeneration.**
    Drops happen only when a `model_deviation` toggle is on AND the user confirms at the Phase 2C /
    Step 2.7 gate; each drop is recorded `DROPPED (deviation)` in the registry + a next_vibes recovery
    breadcrumb. Net-new is propose→build (recorded in the handoff, built by the ETL skill; no
    metamodel write). Absence of data never triggers a `remove_product` in next_vibes (bright line).
    Deviation is knob-blind on `output_model`.
