# CLAUDE.md — vibe-model-skills

Guidance for Claude Code (and Genie Code) working in this repo. Read this first; it explains
**what these skills are for, how they fit together, and the conventions for working on them.**

## What this repo is

A suite of skills for the **"AI-ready data" agentic modeling motion**: they take a **vibe data
model** (a coherent, documented business model generated by the vibe-modeling agent) and **form it
to a customer's real data** — building, validating, and documenting the pipelines domain by domain,
inside the customer's Databricks workspace via Genie Code.

The customer-facing framing: a generated vibe model is a **coherent starting point**; these skills
bring it alive against real data in a **disciplined, phase-gated loop** — not a roaming agent. Four
skills form the loop, taken **one domain at a time**, plus a cross-cutting execution-discipline
skill and a steady-state sync skill:

| # | Skill | Loop station | What it does |
|---|-------|--------------|--------------|
| 1 | `domain-model-assessment` | **Assess** | Inspects the empty target model, profiles bronze, **folds existing production silver/gold into the domain**, produces source-to-target mapping + gap registry + fit grades (Full/Partial/Blocked), and generates pre-filled handoff docs for the build skill. Bootstraps `conventions.yml` interactively (Phase −1) if absent. Opt-in `model_deviation` block (default-OFF) enables gated + logged drops / net-new additions. Always emits `next_vibes.md` (model-refinement artifact). Read-only. |
| 2 | `etl-development-framework` | **Build** | Turns the assessment handoff into pipelines to the customer's naming + engineering standards: DDL (PK/FK/CHECK/comments/CLUSTER BY), Type-1 MERGE notebooks, a DQ validation notebook, and a DAB job. |
| 3 | `domain-model-validation` | **Validate** | Proves the load landed as intended (0 FK orphans, 0 dropped rows, no silent nulls), writes per-table narrative + regression notebooks, `_validation_*` metadata tables, a scorecard, and a quality dashboard. Read-only + metadata writes. |
| 4 | `domain-documentation` | **Document** | Diátaxis docs (tutorials, how-to, reference, explanation), a Model Guide entry-point notebook, and an **auto-generated Genie space** so the domain is queryable in natural language the moment it's built. |
| — | `autonomous-validation` | *(cross-cutting)* | Execution-discipline guidance for Genie Code running at scale: scratchpad-validate → confirm → persist, batching discipline, and the human-in-the-loop contract (run until a gate; self-grade and report, don't prod). Loaded alongside the loop skills, not a station. |
| — | `domain-sync` | *(steady-state)* | Keeps a built model's artifacts in sync after point updates. Change→artifact impact matrix, `synced-against` stamps + staleness linter, scoped regeneration, and generates `ARCHITECTURE.md` + `NEXT_STEPS.md`. Loaded after the model exists, when a maintainer makes a point fix. |

**Handoff is through documents, not chat.** The assessment's output docs
(`business_requirements.md`, `etl_detailed_spec.md`, S2T mapping) *are* the build's input.
Discovery runs once; everything downstream inherits it. This is the "engineered loop, human at
the decisions" property that lets the motion be trusted with production work.

Every loop station emits `docs/commentary/{skill}-improvement-recommendations.md` on completion (protocol: `autonomous-validation/commentary-protocol.md`) — a per-run, self-improving feedback artifact.

**Scope reality:** the loop's fast path delivers a coherent, documented, validated **silver**
layer. Deep BU-specific business logic / metrics (gold) still need human definition, but the
same skills accelerate the gold/metrics layer — especially when there are existing
dashboards/KPIs to grade generated metrics against.

## The two config knobs

Everything a customer/domain needs lives in one `conventions.yml`. Two orthogonal knobs shape the
build (2 × 3 = six combinations; see `templates/conventions-variants/`):

- **`output_model`** — the model *shape*: `normalized` (3NF SSOT port of the vibe model) ·
  `dimensional` (Kimball star) · `hybrid` (normalized silver → a dimensional gold star built
  downstream from it — layered, not both-at-once).
- **`etl_type`** — the build *mechanism*: `merge_notebook` (DDL + Type-1 MERGE trio + daily job) ·
  `sdp_pipeline` (one whole-domain Lakeflow Declarative Pipeline).

Naming/key strategy resolves **per `output_model`** (and per layer in `hybrid`) — see
`etl-development-framework/naming-standards.md` "⚠️ Precedence & key strategy by mode". `examples/`
ships a runnable instance of all six combinations against one model
(`examples/field_service/conventions.field_service.*.yml`).

## Working conventions

- **Skill format:** each skill is a `SKILL.md` + supporting reference `.md` files (+ optional
  `templates/`). Edits to guidance go in these files. Keep the "What this skill produces" and
  "When to Load" sections honest — they drive whether the skill fires.
- **Databricks work:** if any operation actually touches a Databricks workspace, use the
  Databricks AI Dev Kit MCP (never the CLI, except DAB `bundle` commands with an explicit
  `--profile`). Most work in this repo is editing skill markdown and the sample dataset — no
  workspace calls needed.
- **The Meridian dataset is a demo, not a deployment target** — don't deploy it or mutate its
  synthetic content unless explicitly asked.
- **Git:** branch before committing substantive skill changes; commit/push only when asked.
  Write commits as [Conventional Commits](https://www.conventionalcommits.org/) — `feat:` for a
  new skill/variant/capability, `fix:` for corrected guidance, `docs:` for clarifications, and
  `feat!:`/`BREAKING CHANGE:` for anything that breaks a skill contract, the `conventions.yml`
  schema, or an inter-skill handoff doc. The prefixes drive the SemVer bump at release time; see
  README "Versioning & releases" and `scripts/release.sh`.
