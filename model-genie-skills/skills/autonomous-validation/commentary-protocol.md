# Commentary Protocol — emit improvement recommendations on completion

**Loaded by:** every loop station (`domain-model-assessment`, `etl-development-framework`,
`domain-model-validation`, `domain-documentation`) at its final-phase closeout. Hosted here in
`autonomous-validation` because it is cross-cutting execution discipline, not a station of its own.

## Why

A run always knows more about the skill's rough edges than the skill's author did. Capture that
before the session ends. This is the **skill**-improvement analog of the assessment skill's always-on
`next_vibes.md` (which improves the **model**): `next_vibes.md` makes the model truer to the business;
this file makes the *skill* better for the next run.

## Output contract

- **Path:** `docs/commentary/{skill}-improvement-recommendations.md` in the domain project folder
  (create `docs/commentary/` if absent).
- **`{skill}`** is the station slug: `assessment` · `build` · `validation` · `documentation`.
- **When:** the FINAL closeout step of the last phase, AFTER the phase's Completion Self-Audit /
  verification pass reports "none remaining". Emit it as the last thing the run does.
- **Always emitted** — even on a clean run. A clean run records what worked and states
  "No blocking issues found this run" so the next run inherits the confidence, not silence.
- **Fold prior items forward:** if the file already exists from an earlier run, read it first and
  carry any still-unresolved recommendation into the new file (mark it `CARRIED FROM <date>`), so a
  recommendation is not lost just because this run didn't hit it.

## What makes a good recommendation

Each issue must be independently actionable by someone editing the skill who was not in the session:

- **Cite the exact target** — the skill file(s) and phase to change (e.g. `phase-protocol.md` Phase 3),
  and the exact column / table / notebook / SQL involved. Never "somewhere in the skill".
- **Tag a severity** — HIGH (would break a run / produce wrong data) · MEDIUM (friction, rework,
  wasted tokens) · LOW (cosmetic / nice-to-have).
- **State what happened, then the root cause, then the concrete skill edit** — the fix is a change to
  the *skill's guidance*, not a one-off patch to this run's output.
- Prefer a copy-paste-ready rule the skill author can drop in over a vague "be more careful".

## Worked mini-example (one filled issue)

```markdown
## Issue 2: Recurring GROUP BY / aggregate bug in drift-check cells

**Severity:** HIGH — affected 5 of 17 notebooks; same root cause each time
**Phase:** 3 (per-table narrative notebooks)

**What happened:** The Drift Check cell mixed `COUNT(*)` (aggregate) with non-aggregated baseline
columns (`b.Baseline_Value`, `b.Tolerance_Pct`) in one SELECT without GROUP BY → Databricks rejected
it with `MISSING_GROUP_BY` / `SQLSTATE 42803`. The Write Results cell in the same notebook already
used the correct subquery form, so the skill "knew" the right shape but applied it inconsistently.

**Root cause:** No canonical aggregate-isolation rule in `table-narrative-template.md`; the pattern
was corrected mid-batch but not propagated back to earlier notebooks.

**Recommended fix for the skill:** In `table-narrative-template.md`, make the subquery form the only
documented Drift Check pattern — `FROM (SELECT COUNT(*) AS cnt FROM t) LEFT JOIN _data_drift_baseline b …`
— and add a rule to `phase-protocol.md` Phase 3 to propagate any mid-batch SQL fix backward before
continuing forward.
```
